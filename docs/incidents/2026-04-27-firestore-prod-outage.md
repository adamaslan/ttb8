# 2026-04-27 — Firestore SSR loaders 500'd in production

**Severity:** medium (homepage + archive page returned 500 to users)
**Duration:** discovered ~22:25 UTC during archive page rollout; mitigated ~22:45 UTC by switching to a static article snapshot.
**Resolved by:** prototype-mode — static JSON snapshot baked into the build.

## Summary

While shipping the new `/correlations-archive` and `/archive/*` pages, we discovered that **the existing `/` route was already returning 500 in production** because the Netlify SSR function could not initialize `firebase-admin`. Both the homepage's daily-article banner loader and the new archive loaders share `app/lib/articles.server.ts` → `app/lib/firestore.server.ts`, so every Firestore-touching route was broken. The new archive page exposed a pre-existing failure rather than introducing a new one.

To unblock the archive launch we cut the live Firestore dependency entirely and switched to a build-time JSON snapshot of today's articles.

## What broke

Two compounding issues:

1. **Firestore env vars were missing on Netlify.** `GCP_PROJECT_ID` and `GOOGLE_APPLICATION_CREDENTIALS_JSON` were never set on the `ttb8` Netlify project. Only Clerk keys were configured. `getDb()` therefore always fell into the `applicationDefault()` branch with no creds available.

2. **`firebase-admin` was not present in the deployed function bundle even after env vars were set.** The site deploys via `netlify deploy --prod --dir=build/client --functions=netlify/functions` — a CLI manual deploy. This path does not run Netlify's esbuild bundler against `node_modules`, so `[functions] external_node_modules = ["firebase-admin"]` in `netlify.toml` was a no-op for this site. The handler's bundled SSR code contained bare `require("firebase-admin/app")` calls but the function package had no `firebase-admin` installed.

A `package.json` declaring `firebase-admin` as a dep, dropped into the function bundle by `netlify/prepare.js`, did not resolve the failure within the incident window — likely because Netlify's CLI manual-deploy does not run `npm install` inside per-function dirs the way Git-triggered builds do.

## Mitigation (deployed)

- Added `app/data/today-articles.json` — a snapshot of all 7 article types from `gcp3_cache` for the current trading day (`daily_story`, `daily_blog`, `daily_correlation`, `blog_review`, `morning`, `macro_pulse`, `ai_summary`).
- Added `app/lib/articles-static.server.ts` — pure-JS reader over the snapshot. No network calls, no `firebase-admin` import.
- Repointed every loader (`/`, `/articles/:slug`, `/correlations-archive`, `/archive`, `/archive/:type`) to the static module.
- Reverted experimental `netlify.toml` `external_node_modules` and `prepare.js` `package.json` injection — they're moot now that no SSR route imports `firebase-admin`.
- Old `app/lib/articles.server.ts` and `app/lib/firestore.server.ts` are left in place but are unreferenced. They can be deleted after we confirm the static path is durable.

## Why a static snapshot is the right prototype move

- The site currently surfaces only "today's article." There is no historical browsing path that requires a live query.
- Read-only Firestore via a Netlify function adds a service-account key, a serverless cold start, and a runtime dep on `firebase-admin` — three failure modes for zero functional gain at this stage.
- A snapshot file in the repo is reviewable, cacheable (immutable per deploy), and survives Netlify env drift.

## Follow-ups (not done in this incident)

1. **Automate the snapshot.** Add a tiny `scripts/snapshot-articles.mjs` (or reuse the gcp3 backend `write_content_local.py`) that writes `app/data/today-articles.json` and runs as a daily Netlify build hook or scheduled GitHub Action that pushes a commit. Until then, the file is regenerated by hand from the gcp3 `fin-ai1` env.
2. **Decide the long-term reader.** Either (a) ship the static-snapshot pattern as the permanent design, (b) move article reads behind the `gcp3` backend's existing `/content` endpoint and proxy from ttb8, or (c) finish the Firestore-on-Netlify story (env vars + bundler config).
3. **Delete dead code** — `app/lib/articles.server.ts` and `app/lib/firestore.server.ts` once option (a) is chosen.
4. **Rotate the Firestore service-account key** generated during incident debugging (`ttb8-firestore-reader@ttb-lang1.iam.gserviceaccount.com`). The key file was deleted locally and the Netlify env var was set, but rotation is cheap insurance and aligns with the 7-day SA-key rotation policy in `gcp3/.claude/rules/secrets.md`.

## Lessons

- **Health-check loaders before shipping.** A 500 on the homepage went undetected because no smoke test runs against production after a deploy. The `/post-deploy-verify` skill exists for the gcp3 backend; ttb8 has no equivalent. Worth adding.
- **CLI manual deploys are not equivalent to Git-triggered builds.** Several `netlify.toml` keys (`[functions]`, `node_bundler`, `external_node_modules`) only take effect when Netlify's build pipeline runs. If a site is deployed via `netlify deploy --prod` from a developer machine, those keys are inert.
- **Don't treat "the daily banner has been there forever" as proof it works.** Until this turn, no one had hit `/` cold in production after the recent re-deploys. The banner had been silently failing inside the error boundary for an unknown number of days.
